# 企业级 AI 知识库系统（MVP）PRD
## 1. 产品概述
### 1.1 产品背景与目标
针对企业在知识管理中面临“复杂文档难解析、传统搜索不精准、大模型回答易幻觉、数据需权限隔离”的痛点，本项目旨在打造一款**轻量化、高精度、全可控**的企业级 AI 知识库系统。
**MVP 目标**：以最低的技术复杂度实现“复杂文档精准入库、双路混合检索、多模型灵活接入、带引用溯源回答”的核心闭环，快速交付 3-5 个种子客户验证商业价值。
### 1.2 核心技术基座（特定约束）
*   **数据库**：采用 `PostgreSQL + pgvector` 统一存储结构化数据、文档元数据、向量数据，并利用 PG 原生全文检索实现 BM25。
*   **重排机制**：放弃依赖外部大模型的重排，采用**纯代码特征加权打分（轻量级 ReRank）**，确保 100% 程序可控且零额外算力消耗。
*   **大模型接入**：构建统一网关层，不仅兼容 OpenAI 格式 API，还需原生支持 Claude、Ollama（本地模型）以及 DeepSeek、Qwen、GLM 等国产主流大模型的灵活配置接入。
---
## 2. 目标用户与场景
*   **知识库管理员**：负责上传/解析文档、配置分块策略、管理文档权限。
*   **普通企业员工**：通过 Web 界面或 API 接口，对内部知识库进行自然语言提问，获取带引用的精准答案。
---
## 3. 核心业务流程
### 3.1 知识入库流程
1. 管理员上传文档（PDF/Word/扫描件等）。
2. 系统调用复杂文档解析模块，提取结构化文本（含表格、版面信息）。
3. 执行 **QA 拆分**：调用大模型将长文本转为“问题-答案”二元组。
4. 生成向量并连同全文检索索引、文档元数据、RBAC标签写入 `PostgreSQL`。
### 3.2 问答检索流程
1. 用户提问，系统判断用户权限范围。
2. **混合检索**：在 PG 库中并行执行 BM25 全文检索与 pgvector 向量检索。
3. **轻量级 ReRank**：对召回结果进行特征加权打分重排。
4. **生成回答**：将 Top N 片段注入 Prompt，调用配置的大模型，流式输出带引用的答案。

## 4. 功能需求详述
### 4.1 文档解析与数据加工模块
*   **复杂格式基础解析**：
    *   **需求**：集成开源解析能力（如 MinerU 或 RAGFlow 的 DeepDoc），支持 PDF（含双栏、基础表格）、Word、扫描件。
    *   **输出**：保留段落层级和表格 Markdown 结构，过滤页眉页脚噪声。
*   **QA 拆分机制**：
    *   **需求**：不直接对原文切块做向量，而是利用大模型将文档内容拆分为多组“问题-答案”。
    *   **实现**：后台异步批处理，向量大模型仅对“问题(q)”字段做 Embedding，“答案(a)”作为上下文附带存储。
### 4.2 混合检索与轻量级重排模块（核心）
*   **混合检索（BM25 + 向量）基于 PG 实现**：
    *   **向量检索**：利用 `pgvector` 插件，建立 HNSW 索引，执行余弦相似度 `<=>` 查询，召回 Top 20。
    *   **全文检索（BM25）**：利用 PG 原生 `tsvector` 和 `tsquery`（需配置中文分词插件如 `zhparser`），计算 `ts_rank`，召回 Top 20。
    *   **RRF 融合**：在应用层使用倒数排名融合公式 `Score = 1/(60+Rank_v) + 1/(60+Rank_bm25)`，合并去重，取初步 Top 15。
*   **轻量级 ReRank（纯代码可控）**：
    *   **需求**：不调用外部重排模型，通过代码逻辑计算特征得分，对 Top 15 进行二次精排。
    *   **打分特征设计**：
        1.  **精准命中加分**：用户 Query 中的专有名词在 Chunk 中出现的频次（TF-IDF 思想）。
        2.  **元数据加权**：Chunk 所属文档的标题与 Query 的相似度加分。
        3.  **位置加权**：信息出现在 Chunk 开头部分适度加分。
        4.  **RRF 基础分**：保留第一步的 RRF 得分作为 Base Score。
    *   **输出**：按最终综合得分降序排列，截取 Top 5 送入大模型。
### 4.3 大模型统一接入层（LLM Gateway）
*   **需求**：支持在系统后台动态配置多个大模型提供商，按场景（如 QA 拆分、对话回答）路由不同模型。
*   **适配器设计**：
    *   **OpenAI 兼容系**：包含 OpenAI、DeepSeek、Qwen、GLM 等（这些厂商均提供 OpenAI 格式 API，仅需配置 `Base_URL` 和 `API_Key`）。
    *   **Ollama 系（本地化）**：支持配置内网 Ollama 地址，调用本地 Qwen/Llama 模型，保障数据绝对不出域。
    *   **Claude 系**：独立适配 Anthropic API 格式，支持长上下文。
    *   **模型管理界面**：提供配置页，可添加模型实例、设置默认对话模型、默认向量模型、设置 Token 限流。
### 4.4 问答生成与溯源模块
*   **强约束 Prompt 模板**：
    ```text
    你是一个严谨的企业知识库助手。
    【规则1】必须且仅能根据提供的【参考资料】回答问题。
    【规则2】如果【参考资料】中找不到答案，必须回答：“当前知识库中暂无相关信息”，严禁编造。
    【规则3】回答时请在对应句末标注引用编号，如[1]、[2]。
    【参考资料】：
    [1] {chunk_content_1}
    [2] {chunk_content_2}
    ```
*   **流式输出与引用高亮**：
    *   后端通过 SSE (Server-Sent Events) 将大模型生成内容流式推送到前端。
    *   前端解析 `[1]` 标记，渲染为可点击的超链接。点击后侧边栏滑出原文档，并高亮定位到该 Chunk 对应的页码和段落。
### 4.5 权限与安全模块（RBAC）
*   **文档级 RBAC 隔离**：
    *   **需求**：MVP 阶段实现基于角色的文档级访问控制。
    *   **实现**：文档上传时打上 `department_id` 或 `role_level` 标签。用户发起检索时，将用户的权限标签作为 **PG 查询的 WHERE 条件前置过滤**，无权访问的文档块直接在 SQL 层被拦截，不参与向量计算，兼顾安全与性能。

## 5. 数据库设计核心表结构 (PostgreSQL)
```sql
-- 文档元数据表
CREATE TABLE documents (
    id SERIAL PRIMARY KEY,
    title VARCHAR(255),
    department_id INT, -- 权限隔离字段
    file_path VARCHAR(500),
    created_at TIMESTAMP
);
-- 知识块表 (融合全文检索与向量检索)
CREATE TABLE document_chunks (
    id SERIAL PRIMARY KEY,
    doc_id INT REFERENCES documents(id),
    chunk_text TEXT,                  -- 原文内容
    qa_question TEXT,                 -- QA拆分的问题
    qa_answer TEXT,                   -- QA拆分的答案
    embedding vector(1536),           -- 向量字段 (pgvector)
    tsv tsvector,                     -- 全文检索字段 (BM25)
    page_num INT,
    department_id INT                 -- 冗余字段加速过滤
);
-- 建立 HNSW 向量索引
CREATE INDEX idx_chunks_embedding ON document_chunks USING hnsw (embedding vector_cosine_ops);
-- 建立全文检索索引
CREATE INDEX idx_chunks_tsv ON document_chunks USING gin(tsv);
-- 建立权限过滤索引
CREATE INDEX idx_chunks_dept ON document_chunks(department_id);
```

## 6. 非功能需求
### 6.1 性能需求
*   **检索延迟**：得益于 PG 的 HNSW 索引和前置权限过滤，单次混合检索 + 轻量级 ReRank 耗时需 < 300ms。
*   **首字响应**：大模型流式输出首字响应需 < 1.5s。
*   **高并发**：轻量级 ReRank 不占用 GPU，系统并发瓶颈仅取决于大模型 API 的并发限制和 PG 数据库连接池。MVP 阶段支持 50 并发无压力。
### 6.2 可靠性与可扩展性
*   **数据库扩展**：若未来数据量突破千万级 Chunk，pgvector 可平滑迁移至专用的 Milvus 或 Qdrant，应用层检索接口无需改动。
*   **解析与入库异步化**：文档上传、解析、QA 拆分、向量化必须放入消息队列（如 Redis）异步执行，避免阻塞主线程。
---
## 7. MVP 阶段砍掉的功能（明确边界）
为保障 2 个月内快速上线，以下功能本期**不做**：
1. 复杂的可视化工作流编排。

2. 基于图谱的 GraphRAG 多跳推理。

3. 段落级/细粒度的 ABAC 权限控制（本期仅做文档级）。

4. 多渠道（钉钉/飞书）IM 接入（本期仅提供 Web UI 和 OpenAI 兼容 API）。
